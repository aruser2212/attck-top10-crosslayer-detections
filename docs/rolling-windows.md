# Точные скользящие окна T1110: rolling v2

Rolling v2 проверяет окно `(t−W,t]` в моменты подходящих событий каждой группы. Это помогает обнаруживать серии, которые делятся между двумя фиксированными окнами v1. Реализованы четыре Hunt: Windows brute force, Windows password spraying, Linux SSH failures и [Kerberos RC4 service-account burst](kerberos.md). Для трёх Windows Hunt доступны отдельные auth-v2/kerberos-v1 адаптеры бесплатного Elasticsearch Basic; непрерывный pipeline поддерживает только два T1110 Hunt. Linux исполняется офлайн. Ниже описан T1110 auth-v2 путь.

Офлайн-runtime и ручной адаптер оценивают конечный набор событий. Для двух Windows Hunt также есть отдельный [непрерывный pipeline v2](continuous.md#непрерывный-rolling-v2): он повторяет ограниченные оценки, сохраняет микросекундные checkpoints и доставляет алерты через SQLite outbox. V1 продолжает использовать свои правила, индексы и состояние; автоматической миграции между версиями нет.

## Семантика

| Правило | Группа | Окно | Условие |
|---|---|---|---|
| Windows brute | `target.user`, `source.ip` | 5 минут | Не менее 10 failed logons |
| Windows spray | `source.ip` | 10 минут | Не менее 15 разных target accounts |
| Linux SSH | `source.ip`, `user.name` | 5 минут | Не менее 8 failed-password событий |

Каждая уникальная временная метка принятого события группы задаёт anchor `t`. Все события группы с такой меткой включаются вместе, после удаления событий на исключительной нижней границе `t−W` и раньше. `window.start` обозначает эту исключительную границу, `window.end` — включительный anchor. Это отличается от фиксированных окон v1 `[start,end)`.

Count и count_distinct вычисляются точно. Повтор одинакового нормализованного `event.id` не увеличивает счётчик; конфликт содержимого при том же ID завершает весь replay ошибкой. Входной порядок строк не влияет на результат. Временные метки нормализуются в UTC с точностью до микросекунд; сравнения границ не округляются до целых секунд.

Только события, прошедшие dataset, where и требования к ключам группы/distinct, создают anchors. Ключи должны быть непустыми строками. Missing/null и несовместимые типы сохраняют трёхзначную семантику предикатов, включая NOT. Неподдержанные условия отклоняются по [схеме v2](../schema/rolling-hunt.schema.yaml).

Having ограничен `gte` с положительным целочисленным порогом для count/count_distinct. Произвольные условия вроде count=0 могут стать истинными лишь при истечении событий без новой входящей метки; такая логика не входит в этот event-anchored контракт. Project обязан включать все поля группы, метрики и обе границы окна.

Каждая подходящая пара group/timestamp выдаёт один результат. Длительная серия может давать несколько результатов с перекрывающимися окнами. Durable runner присваивает каждой такой паре устойчивый alert ID; повторная оценка того же anchor обновляет документ, но следующий подходящий anchor создаёт отдельный документ. Для Windows отдельный [episode pipeline](episodes.md) группирует эти результаты по точному rule/group и временному gap, сохраняя все исходные алерты. Он показывает число anchors и пиковые метрики окон; метрики перекрывающихся окон не складываются. Подтверждение инцидента остаётся задачей анализа контекста.

## Пример пересечения границы

Команды выполняются из корня репозитория после `make setup`. Создадим инертный пример: пять ошибок в `00:04:59`, ещё пять — в `00:05:01`, для одного аккаунта и IP.

```bash
.venv/bin/python - <<'PY'
import json
from pathlib import Path

events = [
    {
        '@timestamp': '2026-01-01T00:04:59Z' if i < 5 else '2026-01-01T00:05:01Z',
        'event.id': f'rolling-demo-{i}',
        'event.dataset': 'windows.security.logons',
        'event.code': '4625',
        'source.ip': '192.0.2.10',
        'target.user': 'lab\\alice',
    }
    for i in range(10)
]
Path('artifacts').mkdir(exist_ok=True)
Path('artifacts/rolling-demo.jsonl').write_text(
    ''.join(json.dumps(event) + '\n' for event in events), encoding='utf-8'
)
PY

.venv/bin/python tools/hunt_engine.py \
  techniques/T1110_Brute_Force/hunts/win_4625_brute_agg.hunt.yaml \
  --events artifacts/rolling-demo.jsonl

.venv/bin/python tools/rolling_hunt.py \
  techniques/T1110_Brute_Force/hunts/win_4625_brute_agg_rolling.hunt.yaml \
  --events artifacts/rolling-demo.jsonl
```

V1 выдаёт ноль алертов: в каждом фиксированном окне всего пять ошибок. Rolling v2 выдаёт один результат:

```json
{
  "window.start": "2026-01-01T00:00:01Z",
  "window.end": "2026-01-01T00:05:01Z",
  "source.ip": "192.0.2.10",
  "target.user": "lab\\alice",
  "fails": 10
}
```

Это проверка конкретной границы на синтетическом примере, не измерение TPR/FPR.

## Bounds и предшествующий контекст

Опциональные `--start A --end B` выбирают anchors в `[A,B)`. Для вычисления их метрик нужен входной контекст `(A−W,B)`, а не только события начиная с A. Bounds передаются вместе, с часовым поясом; выравнивание по пяти- или десятиминутным границам не требуется.

```bash
.venv/bin/python tools/rolling_hunt.py \
  techniques/T1110_Brute_Force/hunts/win_4625_brute_agg_rolling.hunt.yaml \
  --events artifacts/rolling-demo.jsonl \
  --start 2026-01-01T00:05:00Z --end 2026-01-01T00:05:02Z
```

Результат остаётся тем же: пять ранних событий входят в контекст, но не порождают результат за пределами целевого диапазона. Офлайн-runtime использует только переданные события и не может доказать, что источник предоставил весь необходимый контекст. При разбиении набора на части передавайте историю W перед каждой границей; иначе можно потерять условия, пересекающие границы частей.

Без bounds оцениваются все подходящие anchors переданного конечного набора.

## Elasticsearch Basic и auth-v2

Сначала поднимите стенд `make lab-up`. Используйте отдельный индекс auth-v2; команды не перезаписывают существующие mappings:

```bash
.venv/bin/python tools/elastic_rolling.py --index attck-rolling-demo create-index
.venv/bin/python tools/elastic_rolling.py --index attck-rolling-demo ingest \
  artifacts/rolling-demo.jsonl
.venv/bin/python tools/elastic_rolling.py --index attck-rolling-demo evaluate \
  techniques/T1110_Brute_Force/hunts/win_4625_brute_agg_rolling.hunt.yaml \
  --start 2026-01-01T00:05:00Z --end 2026-01-01T00:05:02Z --page-size 2
```

Ожидается тот же один результат. `create-index` запускается один раз для выбранного нового имени. Повтор ingest с теми же событиями идемпотентен; конфликт ID — ошибка. Настройки URL и credentials описаны в [Elastic](elastic.md); секреты передаются через окружение.

Auth-v1 индексирует время как `date`, с миллисекундной точностью. [Auth-v2](../profiles/elastic/auth-v2.mapping.json) использует `date_nanos`, чтобы сохранить микросекунды нормализованного входа. Это не восстановление исходного 100ns-разряда Windows во времени события: он сохраняется в event identity согласно [контракту нормализации](telemetry.md). Диапазон auth-v2 — от `1970-01-01T00:00:00Z` до `2262-04-11T23:47:16.854775Z` включительно; офлайн-runtime не ограничен этим диапазоном Elasticsearch.

Адаптер читает исходные события через PIT/search_after, включая необходимый контекст, затем запускает точный Python rolling-runtime. Это не встроенная rolling-агрегация Elasticsearch. Даже если одинаковые timestamps разделены страницами, вычисление выполняется после чтения всего ограниченного набора. Приблизительная cardinality не используется.

Границы range-query передаются с обязательными шестью дробными цифрами, включая `.000000Z`. Без дробной части Elasticsearch округляет исключительную нижнюю границу `gt` до конца секунды и может потерять событие, пришедшее на 1 микросекунду позже неё. Этот случай проверяется отдельной native-регрессией.

Проверяются конкретный индекс/UUID, целостность поисковых ответов, порядок пагинации, согласованность `event.id` с `_id` и строгий профиль входа. Смена UUID, partial shards, timeout, некорректные события и неполный refresh завершаются ошибкой. Ingest требует проверяемого refresh и при повторе уже существующих ID, чтобы успех означал видимость событий в последующем поиске.

Auth-v2 принимает только поддержанный Windows authentication dataset. Это более узкий контракт, чем произвольный офлайн JSONL. Смешанный или некорректно типизированный набор может быть отклонён при ingestion, даже если офлайн-фильтр исключил бы отдельные строки.

## Непрерывная обработка и поздние события

`tools/run_rolling_pipeline.py` соединяет тот же auth-v2 адаптер с файловым spool и отдельным `RollingDetectionRunner`. Для него нужны новые source/sink индексы, профиль [alerts-v2](../profiles/elastic/alerts-v2.mapping.json) и отдельная директория состояния. Полный пример атомарной публикации fixture, первого запуска и restart приведён в [continuous.md](continuous.md#непрерывный-rolling-v2).

Checkpoint `C` означает, что anchors строго раньше C уже оценены. Один проход задаёт:

- `A = max(initial_start, C − lookback)` — начало повторной оценки anchors;
- `B = min(now − allowed_lateness, C + max_forward_span)` — исключительный конец нового диапазона;
- `[A,B)` — anchors, чьи результаты можно создать, изменить или отозвать;
- `(A−W,B)` — события, необходимые для расчёта каждого правила.

Первый `C` равен `--start`. Контекст перед `--start` читается из source index и может повысить метрику первого разрешённого anchor. Выравнивания времени по окнам нет, микросекунды сохраняются. Если часы ещё не достигли первого разрешённого диапазона, проход не создаёт будущие anchors. Lookback может быть больше forward span: продвижение считается от C, поэтому повтор старой истории не мешает догонять новый диапазон.

Источник должен сохранять весь нужный диапазон `(A−W,B)` до завершения расчёта. Это особенно важно при отставании checkpoint: срок хранения нельзя выбирать только по текущему времени и lookback. Удаление ещё нужного контекста, включая автоматическую retention-политику, уменьшает метрики и может отозвать прежние алерты; runner не отличает такое удаление от исправления исходных данных.

Lookback ограничивает **anchors**, а не возраст поступившего события. Позднее событие `s < A` ещё может изменить результат в `t ≥ A`, если `t−W < s ≤ t`; само s уже не создаст старый anchor. Результаты с anchors раньше A автоматически не пересматриваются. У источника нет ingest timestamp: полнота обработки всех опозданий и их число неизвестны.

Для каждой пары rule/group/anchor runner сохраняет стабильный ID. Изменение count обновляет revision того же документа. Если повторная полная оценка `[A,B)` больше не подтверждает сигнал, документ получает `status: retracted`, сохраняя последние подтверждённые метрики. Возврат условия активирует тот же ID новой revision. Отзыв ограничен `window.end` в `[A,B)`, а не положением `window.start`.

Все результаты одного прохода, checkpoints и outbox записываются одной SQLite-транзакцией. Превышение лимитов, неполный поиск или смена source UUID не продвигают checkpoint. Доставка в Elasticsearch повторяемая: document ID и `external_gte` с монотонной revision защищают от дубликатов и запоздавшей старой записи. Между SQLite и Elasticsearch нет общей распределённой транзакции; после сбоя подтверждение доставки может потребовать повтора.

## Лимиты и область доказательств

По умолчанию `--max-events` ограничивает вход 100 000 событиями, `--max-alerts` — результат 10 000 алертами. Офлайн-лимит считается по сырым строкам-событиям до дедупликации и фильтрации, включая события вне bounds. В native replay ограничивается прочитанная популяция Windows-событий в диапазоне поиска, до локального where. Повторы и неприменимые события не дают обходить лимит.

Эти флаги относятся к replay/evaluate. Команда `elastic_rolling.py ingest` их не принимает; она проверяет и загружает переданный конечный JSONL-файл.

У непрерывного pipeline отдельные флаги: `--max-query-events` ограничивает полный запрос каждого правила вместе с контекстом, а `--max-alerts` — сумму кандидатов и новых отзывов всех правил текущей оценки. Уже сохранённый outbox доставляется до неё; уменьшенный лимит не отменяет эти прежние записи. `--max-forward-seconds` ограничивает продвижение checkpoint; по умолчанию 3600 секунд. Оставшаяся история даёт `catching_up` и требует следующих проходов. Уменьшение forward span не устраняет превышение лимита, вызванное плотным lookback или контекстом окна: в таком случае нужны достаточный лимит и ресурсы, а не неполная оценка.

Превышение лимита завершает весь вызов ошибкой, без частичного успешного JSON. `--page-size` задаёт размер страницы Elasticsearch, а не максимальный размер всего набора. Ограниченный набор обрабатывается в памяти; эти счётчики не являются пределом размера отдельного события в байтах или результатом нагрузочного benchmark.

`make check` включает контрактные тесты, [ручные fixtures](../tests/fixtures/rolling/auth_cases.json), независимый O(n²) oracle и проверки совместимости v1/v2. `make check-elastic` исполняет отдельный native suite на настоящем Elasticsearch Basic. Фактические результаты запусков приведены в [отчёте](validation_report.md).

Следующие задачи сосредоточены на [качестве детектов](detection-priorities.md) и проверке на репрезентативной рабочей телеметрии. Реализованные инкрементальная группировка и архивы описаны отдельно; дальнейшее расширение хранения отложено. Ограниченный rolling replay, durable scheduler и episode grouping не устанавливают полноту бесконечного потока и не измеряют эксплуатационную точность.
