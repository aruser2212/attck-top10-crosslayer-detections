# Методология и критерии качества

Цель — воспроизводимые детекты с описанными границами применимости: источник события → нормализация → правило → ожидаемый алерт → tuning на репрезентативных данных.

## Что означает Top-20

Это авторская подборка двадцати семейств техник для Windows/Linux detection engineering, расширенная с исходных десяти. Это не официальный рейтинг MITRE и не статистическое утверждение о частоте атак. Исторический URL репозитория сохранён. Уровень исполнения каждого семейства указан в [портфеле](portfolio.md): число каталогов не означает двадцать непрерывных SIEM-детекторов. Карточки могут включать дополнительные техники контекста: например, webshell относится к T1505.003, удаление теневых копий — к T1490. Событие после эксплуатации само по себе не подтверждает T1190.

Разметка проверяется по закреплённому официальному **Enterprise ATT&CK v20.0, STIX 2.1** из `mitre-attack/attack-stix-data`, commit `20664a889568dce884a1dac0ec7b12ae3a199f51`. Компактный каталог хранит 867 техник/подтехник, 15 канонических тактик, статусы revoked/deprecated и связи замены. Источник, исходный SHA256 и checksum производного каталога записаны в [metadata](../profiles/attack/metadata.json).

`python tools/check_attack.py check` выполняет офлайн-проверку идентификаторов и тактик DetCard/Sigma. Неизвестные, revoked/deprecated ссылки активных артефактов приводят к ошибке; различие первичной разметки и контекста требует review. При обновлении каталога нужно отдельно пересматривать наблюдаемую технику, тактику и subtechniques. Совпадение семейства и подтехники не считается ошибкой само по себе, но разные подтехники не взаимозаменяемы.

Первичные `tactics` и Sigma-теги отражают канонические фазы выбранных техник. Более широкий контекст цепочки атаки сохраняется в примечаниях карточек и не расширяет заявленное покрытие. Например, парольный подбор может предшествовать initial access, но первичная тактика T1110 — credential-access. Проверенная миграция Linux log clearing и изменения тактик v20.0 описаны в [ATT&CK mapping](attack-mapping.md). Исторические ID карточек и имена каталогов сохраняют совместимость ссылок.

## Жизненный цикл

| Статус | Критерий |
|---|---|
| draft | Логика или требования к источникам ещё уточняются. |
| test | Правило предназначено для проверки и настройки; отдельные успешные тесты не означают пригодность для production. |
| stable | validation.status=tested, ссылки на данные, воспроизводимый replay всех заявленных артефактов в указанном окружении, review нормализации и характерных benign-сценариев. Среда и ограничения описаны. |
| deprecated | Артефакт сохранён для совместимости, причина и замена указаны. |

Валидатор проверяет необходимые машинные условия для stable; полноту доказательств проверяет reviewer. Stable не означает отсутствие ложных срабатываний во всех средах.

## Виды доказательств

1. Структура и разметка: JSON Schema, уникальные ID, существующие ссылки, YAML без повторных ключей, офлайн-проверка техник/тактик по закреплённому ATT&CK.
2. Формат/движок: pySigma parsing, libyara compilation, Suricata loading. Валидный синтаксис не доказывает обнаружение.
3. Синтетические предикаты: изолированные положительные/отрицательные события проверяют условия Sigma и YARA с явным профилем источника.
4. Replay: исполнение поддерживаемого Hunt, PCAP в Suricata, настоящие агрегации Elasticsearch Basic с ожидаемыми результатами.
5. Эксплуатационная оценка: репрезентативная телеметрия, проверенные метки, период и состав выборки, tuning, нагрузка и задержка.

Partial указывает на ограниченную проверку части артефактов. Tested требует соответствия всему заявленному scope карточки. В карточках нужны ссылки на evidence и описание непроверенной части.

## Точность

TPR = TP/(TP+FN); FPR = FP/(FP+TN). Нужно определить единицу наблюдения: событие, пользователь, окно или атака. Precision = TP/(TP+FP) зависит от доли атак в выборке. Прохождение вручную подобранных fixtures не даёт эксплуатационных TPR/FPR: эти поля остаются null до измерений на определённой выборке.

Для каждого детекта нужны benign lookalikes, отсутствующие поля, неверный источник, границы окна, повторная доставка и искажения нормализации. Не следует подавлять событие только по имени executable. Доверие к пути, подписи или владельцу требует реально доступного enrichment.

Сетевые HTTP-правила требуют видимого HTTP; зашифрованный TLS/SMB не позволяет делать те же выводы без соответствующей точки наблюдения. SSH-сигнал считает сессии, а не ошибки пароля. Успешный write-class auditd event показывает намерение записи, а не обязательно изменение содержимого. Совместимость сетевых правил со Snort не проверена.

## Воспроизводимость

Логические изменения сопровождаются fixtures и changelog. Direct dependencies заданы в requirements-dev.in, полный набор с SHA256 — в requirements-dev.lock. Образы Elastic и Suricata закреплены digest. Обновление инструмента требует повторения соответствующих проверок.

ATT&CK обновляется отдельным проверяемым изменением: выбор версии и commit, загрузка официального STIX с проверкой TLS, фиксация исходных bytes/SHA256, детерминированная генерация каталога и review изменившейся разметки. Runtime lint не обращается к сети и не проверяет ежедневно наличие новых релизов. Checksum фиксирует содержимое относительно сохранённых метаданных; проверка цифровой подписи MITRE или неизменности upstream-тега не заявляется. Атрибуция исходных данных сохранена в [NOTICE](../profiles/attack/NOTICE.txt).

`make check`, `make check-network` и `make check-elastic` проверяют разные уровни. Отсутствующая служба или пропущенная suite не считаются успехом replay. Inventory содержит commit, признак незакоммиченных изменений и версии инструментов. Локальная проверка не означает, что GitHub Actions уже выполнялся.
