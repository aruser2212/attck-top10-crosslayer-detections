## Выполненные локальные проверки

Последний локальный запуск 2026-11-07: `make check` — **3305 passed**, `make check-elastic` — **528 passed**; в выполненных pytest-наборах нет failures/errors/skipped. Основной набор явно исключает 529 тестов: 528 Elastic-тестов и один Docker replay-тест. Полный Basic-набор включает прежние 346 проверок и 182 новых проверки Windows process-v1.

Общий HTTP-клиент Elasticsearch дополнен 40 проверками транспорта: redirect 301/302/303/307/308 отклоняется после единственного исходного запроса, включая смену origin, HTTPS → HTTP, относительный, пустой, отсутствующий и некорректный `Location`. Проверяются API key/Basic/anonymous, JSON/NDJSON, обычные запросы, сохранение HTTP status и отсутствие приватных значений в сообщении ошибки. Используется настоящий urllib opener с подменой только сетевого ввода-вывода. Глобальный opener приложения не меняется; полный Basic-набор проверяет обычный путь к лабораторному серверу.

Расширение до [20 семейств](portfolio.md) добавило десять Windows process-правил.
Их 169 ручных сценариев включают 50 кандидатов, 19 ожидаемых легитимных
совпадений, 84 несовпадения и 16 отклонений профиля. Отдельно прошли 141
проверка профиля/XML, 88 core/adapter-проверок, 180 fixture-проверок и 182 native
Basic-проверки. Эти тесты включены в текущие полные наборы. Нативное вычисление
использует именованные запросы и для каждого прочитанного события сравнивает
rule IDs с офлайн-результатом; исходные поля проверяются и для несовпадений.

`make demo` выполнен как документированная команда: корректный JSON с
`checks_passed: 7`, по одному ожидаемому кандидату для каждого сценария.
Семь тестов demo входят в общий локальный набор, включая запуск вне каталога
репозитория и отказ без частичного успешного отчёта.

Ранее реализованный LSASS-пилот сохраняет 443 локальные проверки: 213 core/profile, 108 нормализации XML, 86 ручных fixtures и 36 adapter. Его 56 Basic-проверок входят в текущий полный набор. LSASS fixtures содержат 40 ручных сценариев / 50 записей: 28 допустимых сценариев и 12 отклоняемых, включая конфликт identity.

Для [NewCredentials](newcredentials.md) добавлены 40 ручных сценариев / 98 записей. Из них 28 допускают корреляцию: 17 `candidate`, один ожидаемый `benign_candidate` и 10 `nonmatch`; ещё четыре вызывают ошибку корреляции, восемь отклоняются строгим профилем. Отдельный native-прогон прошёл все 60 проверок; те же проверки включены в полный Basic-набор. Они покрывают конечную корреляцию 4624/4672, границы времени, неоднозначность сессии, полное чтение конечного набора dataset `windows.security.sessions` в профильном индексе, лимиты и XML → CLI → алерт. Предикат Office → PowerShell дополнен полной формой `-EncodedCommand`; с учётом десяти новых process-правил Sigma-набор теперь содержит 302 примера.

Отдельно воспроизведены 21 публичная Sysmon 10 v3 запись из двух закреплённых EVTX-источников: один ожидаемый кандидат и 20 событий, не удовлетворяющих предикату. Строгая нормализация, полные алерты офлайн/Basic и immutable retry совпали. Время экспортировано из целого FILETIME без потерь от float; источники, лицензии, SHA256, воспроизводимые команды и ограничения разметки приведены в [разборе публичных данных](public-data.md). Это проверка поведения на выбранных лабораторных записях, не измерение эксплуатационной точности.

Публичный NewCredentials EVTX дал два события — 4624 v0 и 4672 v0 — и одного кандидата с разницей времени **0 µs**. Полные результаты офлайн и Basic совпали, повторный ingest добавил ноль записей. Источник не содержит подтверждения общей загрузочной сессии Windows: `host.boot.id` задан явно как допущение для выбранной пары. Это условный replay, не проверка подлинной boot identity или доказательство PtH. Закреплённый источник описан в [manifest](data/newcredentials-public-source.json), результат и ограничения — в [разборе публичных данных](public-data.md).

2026-11-07 также выполнен [ограниченный benchmark](benchmarks.md): 18 успешных samples для конечного офлайн-replay rolling v2 и LSASS. Проверены ожидаемые результаты и повторяемость SHA256 входов/алертов. Параметры, время и память приведены в отдельном отчёте; NewCredentials, native Basic и непрерывный pipeline этим измерением не охвачены.

Сетевые правила и Docker replay в этом этапе не менялись. Последний `make check-network` выполнен 2026-11-07: Suricata 8.0.4 загрузила все 9 SID и успешно воспроизвела 25 PCAP-сценариев (510 пакетов). Три регрессии вывода Docker входят в текущий `make check`. Числа разных уровней не суммируются как независимые проверки точности.

`make setup` с hash verification и `make lab-up` проверены; Compose поднял лабораторный кластер с постоянным named volume. Проверены как конечная последовательность create-index → ingest → evaluate, так и subprocess CLI непрерывного pipeline: ограниченная очередь, повторные запуски, позднее событие, обновление одного алерта и корректная остановка watch по SIGTERM.

Отдельная локальная проверка `docker compose down` → `up -d --wait` подтвердила сохранение UUID обоих индексов, 10 событий, одного алерта с прежним ID/revision и повторное использование SQLite state. Это проверка пересоздания контейнера с сохранённым томом, не backup/restore или отказоустойчивость нескольких узлов.

Новый rolling CLI воспроизведён отдельно от API-тестов: create-index → ingest → повтор ingest → bounded evaluate, в том числе при запуске вне каталога репозитория. Серия из пяти ошибок в `00:04:59` и пяти в `00:05:01` даёт один rolling-алерт с count=10; v1 на тех же данных возвращает ноль. Повтор ingestion добавляет ноль событий. Это подтверждает конкретный синтетический граничный случай, а не эксплуатационную TPR.

Документированный durable v2 пример из `continuous.md` также выполнен отдельными процессами на Basic: атомарная публикация fixture → `--once --initialize` → повторный `--once`. Получен один active-алерт с `fails=10`, окном `(00:00:01,00:05:01]` и revision 1; повтор сохранил тот же ID/revision, outbox пуст. Использовались отдельные временные индексы. Это дополнение к 15 native-проверкам нового runner/pipeline, а не тест реального Windows collector.

Пример из `episodes.md` выполнен реальными CLI-командами на Basic: 12 событий создали три исходных алерта с `fails=10/11/12` и один open-эпизод с `anchor_count=3`, `peak_metrics.fails=12`. Повтор сохранил revision 1. Продвижение исходного checkpoint на 1µs за `last_anchor+gap` закрыло тот же эпизод с revision 2. Все три raw-алерта сохранились, outbox пуст. Использованы отдельные временные индексы; это проверка группировки и состояния, а не оценка снижения реальных ложных срабатываний.

Следующий документированный прогон сравнил `--projection-mode full` с режимом incremental на той же БД и создал два проверяемых архива. Для неизменившегося закрытого эпизода incremental сообщил `groups_recomputed=0`; документ сохранил revision 2. Первый архив содержал `replay_stable_episodes=0`, а после продвижения checkpoint за строгую границу — 1. Оба прошли offline verify, все три raw-алерта остались в живом индексе. Это подтверждает конкретный контракт архивирования без очистки, а не нагрузочную производительность или восстановление работающей SIEM.

Числа сценариев разных проверок не складываются в показатель полноты покрытия: один pytest-test может исполнять целый manifest, а некоторые тесты проверяют ошибки контракта. Источник итоговых чисел pytest — JUnit-артефакты соответствующего локального прогона.

## Воспроизведение

Требуются Python 3.12, Make, Docker и Compose v2. Из корня репозитория:

```bash
make setup
make check
make check-network
make lab-up
make check-elastic
make lab-down
```

- `make check` запускает проверку структуры, закреплённого ATT&CK, актуальности генерируемых Elastic-запросов, локальные тесты и проверку актуальности coverage. Network и integration suites исключены из этой команды явно и запускаются отдельными командами.
- `make check-network` загружает правила и исполняет PCAP replay в закреплённом образе Suricata. Отсутствующий Docker/движок или несоответствие ожидаемым алертам означает ошибку, а не успешный пропуск.
- `make check-elastic` обращается к настоящему Elasticsearch, проверяет Basic-лицензию и выполняет integration suite. По умолчанию используется локальный стенд; параметры существующего сервера описаны в [Elastic](elastic.md).

Офлайн-корреляцию можно воспроизвести отдельно:

```bash
.venv/bin/python tools/correlate_webshell.py \
  tests/fixtures/correlation/webroot_request.jsonl \
  --webroot /var/www/html
```

Ожидается ровно одна пара `file-create → request-suspicious`; запрос другого хоста и обычный похожий query не входят в результат. Одна повторная доставка file event учитывается как duplicate. Документированный Basic-пример из [correlation guide](correlation.md) выполнен отдельными CLI-процессами: четыре уникальных события, та же пара с namespace `site-1` и разницей 60 секунд, повторный ingest добавляет ноль записей. Временный индекс удалён после проверки. Это проверка нормализованного синтетического входа, а не живого сбора журналов.

## GitHub Actions и ограничения

Workflow содержит отдельные jobs для структуры/предикатов, Suricata replay и Elasticsearch Basic. Этот отчёт фиксирует подтверждённые локальные запуски. Статус удалённого CI проверяется отдельно для опубликованного commit на странице GitHub Actions; локальное прохождение не подменяет этот результат.

Обновлённый workflow использует Ubuntu 24.04 и официальные Node 24 actions,
закреплённые по SHA: checkout v7.0.1, setup-python v7.1.0, upload-artifact v7.0.2.
Версии, commit SHA и `action.yml` проверены по официальным GitHub-репозиториям;
demo JSON включён в evidence основного job.

Непрерывные Windows-пилоты v1 и rolling v2 с отдельным состоянием и обработкой поздних событий в ограниченном lookback реализованы. Автоматической миграции между ними нет. Представление эпизодов сохраняет raw-сигналы, пересчитывает затронутые группы и поддерживает полный эталон; согласованное evidence можно экспортировать и проверить офлайн. Полное чтение истории и её лимиты сохраняются.

Точная конечная корреляция NewCredentials 4624/4672 реализована офлайн и на Basic. Следующий приоритет — [качество детектов](detection-priorities.md): trusted collector с подтверждённой boot identity для Windows session joins, репрезентативная легитимная NewCredentials-телеметрия и реальные профили AV/EDR для LSASS-пилота. Для реализованной host/web-корреляции остаются нативные source mappings и контекст deploy. Остальные 18 Hunt по-прежнему проектные описания: отдельные host/web, LSASS и NewCredentials runtimes не реализуют их DSL автоматически. Калибровка operational metrics и проверка реального collector остаются необходимыми. Дальнейшее расширение журналов, очистки истории и планировщиков отложено; Linux Elastic-профиль и новые SIEM добавляются вместе с проверкой конкретных сценариев по [плану](roadmap.md). Успешные synthetic cases не используются для заявления «100% точности».
