# Roadmap

Цель проекта — переносимые детекты с воспроизводимыми доказательствами поведения и описанными ограничениями. Приоритет ближайшего этапа — точность условий, связи между источниками и проверка на бесплатном Elasticsearch Basic.

Ниже описано состояние исходников проекта. Новый версионный релиз, включая v0.3, ещё не объявлен; отправка кода в GitHub и прохождение проверок сами по себе не создают release/tag.

## Граница библиотечного выпуска

Текущий объём — 20 семейств, 30 DetCards и 30 Sigma rules. Новые десять
[Windows process сценариев](windows-process.md) имеют строгий Sysmon 1 v5 профиль,
конечный офлайн replay и нативные запросы Elasticsearch Basic с проверкой каждого
совпадения. [Quickstart](quickstart.md) и `make demo` дают единый вход в семь
исполняемых сценариев библиотеки. Новые правила не добавляют legacy Hunt.

Завершение этого выпуска означает согласованный каталог, выполняемые примеры,
ручные ожидания и успешные проверки заявленных движков. Оно не требует расширять
число техник дальше двадцати, писать очередной планировщик или объявлять
неизмеренные эксплуатационные метрики. Результаты фиксируются в
[validation report](validation_report.md); требования следующего этапа ниже
относятся к рабочим данным и отдельным источниковым интеграциям.

## После библиотечного выпуска: рабочие данные и точность

[Разбор 19 исходных legacy Hunt](detection-priorities.md) фиксирует конкретные пробелы условий. T1558.003 burst переведён в исполняемый v2 и проверен на Basic; осталось 18 проектных описаний. Остаток сокращается после проверки поведения и backend, а не от одного добавления версии схемы.

1. Для реализованного RC4 TGS пилота собрать репрезентативную benign-телеметрию и проверить порог/контекст сервисов. Синтетическая и Basic-проверка реализации завершены; эксплуатационная точность пока не измерена.
2. Host + web: конечный Basic replay, обязательная файловая область и ручные deploy/upload/admin примеры реализованы. Следующий шаг этого сценария — проверенный native mapping обоих источников и обогащение процессами/контекстом deploy; совпадение пока остаётся кандидатом.
3. LSASS ProcessAccess: отдельный конечный пилот проверяет бит `PROCESS_VM_READ`, GUID обоих процессов и строгий Sysmon 10 v3 профиль. Следующий шаг — проверка реальных профилей AV/EDR и источников по [контракту](lsass.md); выданное право чтения не подтверждает чтение памяти или дамп. Общий Hunt DSL для этого legacy-описания пока не реализован.
4. NewCredentials/4672: отдельный [конечный пилот](newcredentials.md) соединяет host/boot/LogonId/SID и проверяет неоднозначность сессии. Дальше необходимы подтверждённый boot scope от реального источника и репрезентативная разметка. Легитимный `runas /netonly` остаётся ожидаемым кандидатом; LT9 и привилегии не доказывают PtH. Общий Hunt DSL этих описаний пока не реализован.
5. Проверить цепочку установки службы, процесса и named pipe на одном контракте источников, включая авторизованный PsExec. Только затем расширять остальные Hunt по ранжированному списку.

Для каждого сценария отдельно описывать успешный кандидат, похожее несовпадение, легитимный кандидат и варианты вне покрытия. Fixtures проверяют исполнение предиката; эксплуатационная precision требует независимой разметки реальной телеметрии. Широкие исключения по имени, basename или суффиксу учётной записи не подменяют эту проверку.

### Реализованный пилот: T1558.003 burst

Исходный Hunt принимал ServiceName за SPN, использовал subject.user, исключал machine requester и не проверял успешность TGS. Исправленный контракт — успешные 4769 с RC4, requester/domain/source IP и точное число разных service SID в `(t−5m,t]`. Добавлены профиль 4769, нормализатор и конечный Basic replay на существующем rolling-движке. [Инструкция](kerberos.md) описывает воспроизведение и ограничения.

RC4 burst — кандидат для расследования. Он возможен у легитимных приложений и не показывает офлайн-подбор пароля. AES-варианты и активность ниже порога не входят в выбранный предикат. Проверены 44 ручных сценария и 53 native-теста, включая XML → CLI → Basic. Результаты и границы доказательств зафиксированы в [отчёте](validation_report.md).

### Порядок проверки каждого детекта

- Определить источник, обязательные поля, identity, нормализацию и наблюдаемый смысл результата.
- Зафиксировать ожидаемые алерты на позитивных, benign и граничных сценариях до оценки backend.
- Реализовать только нужную семантику: точное окно или join, регистр, дубликаты и явное поведение при неполных данных.
- Сравнить офлайн-результат с настоящим Elasticsearch Basic и сохранить evidence; не требовать платной лицензии или trial.
- Обновить DetCard, тест-план и ограничения по фактически выполненной проверке. Наличие теста не означает его прохождения; наличие совпадения не доказывает атаку.

Расширение журнала изменений источника, pruning, архивирования, планировщиков и распределённой координации отложено. Реализованная инфраструктура сохранена ниже как основа; её дальнейшее развитие не является ближайшей целью проекта.

## Реализовано: первые исполняемые сценарии

### T1110 и бесплатный Elasticsearch Basic

Три Hunt v1 исполняются на конечном наборе нормализованных событий: Windows brute force, Windows password spraying и Linux SSH failures. Положительные, отрицательные и граничные fixtures задают ожидаемые алерты.

Для Windows-пилота добавлены профиль полей, нормализация экспортированных Security Event XML, исполняемый адаптер Elasticsearch Basic и интеграционные проверки на настоящем сервере. Composite pagination считает разных пользователей точно, без приблизительной cardinality. Платная лицензия и trial не требуются.

Для Linux добавлен нормализатор экспортов `journalctl --output=json`: поддержаны явно определённые sshd-сообщения об ошибке пароля и успешном входе. Время и идентичность берутся из journal-полей; недостающие значения не выдумываются. Нормализованные события проверяются офлайн Linux Hunt. Отдельный Linux-профиль Elasticsearch и развёртывание journal-коллектора ещё не реализованы.

Три Hunt v1 используют фиксированные неперекрывающиеся UTC-окна. Для двух Windows-правил также доступен ограниченный непрерывный pipeline, описанный ниже. Поддержка остальных возможностей Hunt DSL не заявлена. Подробнее: [Hunt DSL](hunt-dsl.md), [Elasticsearch Basic](elastic.md).

### Точный rolling replay v2

Добавлены три отдельные версии T1110 Hunt со скользящим окном `(t−W,t]`, проверяемым в моменты подходящих событий каждой группы. Все события с одинаковым timestamp учитываются вместе; count и count_distinct вычисляются точно. Положительные целочисленные пороги `gte` ограничивают область поддержанной логики. Проверки границ, микросекунд, повторов, истечения distinct-значений и разбиения replay на части используют явные ожидаемые результаты и независимый математический oracle.

Два Windows rolling-правила имеют отдельный адаптер бесплатного Elasticsearch Basic с профилем auth-v2/date_nanos. PIT и search_after возвращают конечный набор событий; точную rolling-логику исполняет Python. Для целевых моментов `[A,B)` читается предшествующий контекст `(A−W,B)`. Ошибка поиска или превышение лимитов приводит к ошибке всего прохода, без успешного частичного результата.

Конечный replay дополнен отдельным непрерывным `tools/run_rolling_pipeline.py`: auth-v2 source, alerts-v2 sink и SQLite state v2 сохраняют микросекундные границы. Ограниченные шаги catch-up продвигают checkpoint, а lookback повторно рассчитывает предыдущие anchors с полным контекстом. Изменённые результаты обновляют ревизию того же alert ID; исчезнувшие результаты получают статус retracted. Outbox сохраняет доставку после сбоя. Правила v1, их шаблоны и состояние сохранены; автоматической миграции нет. Один подходящий group/timestamp даёт один результат; объединения в инциденты и подавления последующих подходящих timestamps пока нет. Linux rolling остаётся офлайн. Подробнее: [rolling windows](rolling-windows.md).

### Корреляция host + web

Отдельный runtime и конечный Basic replay связывают успешное create/write файла в webroot с последующим HTTP-запросом по точным host.id, resource.namespace и каноническому POSIX пути. Проверяются направление времени, latest eligible write, границы микросекунд, точные query keys, дубликаты и обычные deploy/upload примеры. Совпадающая легитимная административная последовательность сохранена в fixtures. Оба источника читаются через один PIT; отдельный профиль проверяет вход до записи и после чтения.

Результат — подозрительная активность, подтверждённая двумя источниками. Он не доказывает эксплуатацию уязвимости или выполнение содержимого файла. Нормализация URL в путь файла и trusted namespace, а также нативный сбор file/HTTP журналов остаются upstream-контрактом. Два legacy Hunt этой техники не объявляются исполняемыми: first_seen и общий join DSL не реализованы. Инструкция и миграция прежнего пилота: [correlation](correlation.md).

### Инструмент оценки по разметке

`tools/evaluate_detection.py` вычисляет confusion matrix, TPR/FPR и precision для заданных размеченных наблюдений и результатов детектора. Контракт определяет единицу наблюдения, идентификаторы, правила сопоставления и происхождение данных; арифметика проверяется синтетическими примерами. Инструмент не запускает детектор и не создаёт ground truth. Репрезентативные размеченные данные пока не собраны, поэтому эксплуатационные показатели проекта не измерены. Подробнее: [evaluation](evaluation.md).

## Реализовано: проверяемая основа

- DetCard проверяются JSON Schema; валидатор обнаруживает дубли YAML/ID, неверные типы, отсутствующие или выходящие за репозиторий ссылки и пустой набор артефактов.
- Определены критерии жизненного цикла и отдельные уровни доказательств. Ни одна карточка автоматически не повышена до stable.
- Зависимости закреплены в lockfile с SHA256; образы Suricata и Elasticsearch закреплены digest.
- Добавлены проверки всех Sigma-правил и их предикатов, загрузка и PCAP replay сетевых сигнатур в Suricata, компиляция и проверки YARA на инертных образцах.
- Исправлены подтверждённые расхождения условий, ATT&CK-разметки и требований к источникам. Linux-артефакты очистки логов связаны с отдельной DetCard.
- Закреплён официальный Enterprise ATT&CK v20.0/STIX 2.1 с источником, commit и checksum. Офлайн-lint проверяет техники, revoked/deprecated и канонические тактики; разметка обновлена по выбранной версии. Это не ежедневная синхронизация с MITRE. Подробнее: [ATT&CK mapping](attack-mapping.md).
- Coverage генерируется из содержимого; JSON inventory сохраняет HEAD, признак незакоммиченных изменений и версии инструментов. Количество файлов отделено от количества правил, тест-планы — от выполненных проверок.

Команды и пределы этих проверок описаны в [отчёте](validation_report.md), критерии качества — в [методологии](methodology.md).

## Реализовано: сопровождающая инфраструктура

Следующие компоненты уже входят в рабочее дерево. Они сохраняются; текущий этап использует их в пределах документированных ограничений.

### Контролируемый непрерывный Windows-пилот

`tools/run_auth_pipeline.py` объединяет файловый ingestion и runner в режимах `--once` и `--watch`. Это работающий локальный путь от опубликованного файла до сохранённого алерта в Elasticsearch Basic:

- Producer атомарно публикует неизменяемые `.ready.jsonl` или `.ready.xml`. Ограниченный по файлам/байтам importer проверяет весь файл перед записью и сохраняет SHA256 и acknowledgment в SQLite. Повторная доставка и восстановление после записи в ES, но до локального acknowledgment, проверены. Повреждённые и изменённые файлы явно отмечаются; автоматического удаления пользовательских файлов нет.
- Пока остаются готовые, но не подтверждённые файлы, pipeline сообщает `catching_up` и не продвигает checkpoint детектора. Сохранённые неизменённые acknowledged-файлы не считаются новым backlog. Это защищает уже видимую очередь от потери событий за пределами replay-окна.
- Runner хранит checkpoints и пересматривает полностью закрытые UTC tumbling windows с настраиваемыми allowed lateness и lookback. Опоздания за пределами этого горизонта не обнаруживаются автоматически: это ограниченная, а не неограниченная обработка поздних событий.
- Транзакционный SQLite outbox сохраняет алерты перед доставкой. Стабильные ID и монотонные внешние версии Elasticsearch позволяют повторять доставку и не дают запоздалой старой ревизии перезаписать новую. Распределённая атомарная транзакция между SQLite и Elasticsearch не заявляется.
- Состояние привязано к конкретным UUID источника и приёмника, профилям и конфигурации правил/расписания. Блокировки исключают параллельное использование одной БД состояния. Изменение области работы требует отдельного состояния; координация нескольких независимых workers пока не реализована.

Native integration suites проверяют реальный Elasticsearch Basic: restart/redelivery, XML-нормализацию, сохранение алертов, восстановление после сбоев, backlog, замену индекса и документированный CLI, включая остановку watch. Точный результат финального прогона хранится в [отчёте и артефактах](validation_report.md); добавление теста само по себе не считается его прохождением.

Pipeline получает подготовленные файлы. Сбор событий с живого Windows-хоста, настройка Windows Event Forwarding/Elastic Agent и эксплуатационное развёртывание ещё не проверены.

### Эпизоды из rolling-алертов

`tools/run_episode_pipeline.py` читает согласованный snapshot локального rolling v2 state и создаёт отдельные документы episodes-v1 в Elasticsearch Basic. Соседние active-алерты одного rule/group объединяются при расстоянии не больше заданного gap. Все исходные сигналы сохраняются; эпизод содержит ID/ревизии участников и максимумы метрик окон, без суммирования перекрывающихся счётчиков.

Закрытие определяется checkpoint исходного правила и допускает поздний пересмотр. Детерминированный ID зависит от самого раннего участника; при изменении этого участника прежний документ отзывается со ссылками на текущие замены. Merge/split, reactivation и восстановление отдельного outbox проверяются синтетическими сценариями. Состояние привязано к конкретному файлу источника и UUID приёмника; откат ревизий/checkpoints и исчезновение исходных строк завершаются ошибкой. По умолчанию перестраиваются группы с новыми/изменёнными исходными ревизиями и группы, пересёкшие границу закрытия. Полный пересчёт сохранён как эталон, режимы дают одинаковые документы. Чтение и проверка всей сохранённой истории остаются ограниченными лимитами. Подробнее: [эпизоды](episodes.md).

### Проверяемые архивы evidence

`tools/episode_archive.py` сохраняет согласованный набор последних raw/episode документов в отдельный JSON-файл. Экспорт требует свободных блокировок writers, пустых outbox и точного совпадения исходного snapshot с обработанным состоянием эпизодов. Повторная запись по занятому имени запрещена. Офлайн-проверка сверяет checksum, структуру и связи, а текущие компоненты — с полным эталоном группировки.

Архив содержит оценку компонентов за пределами текущего bounded replay: `last_anchor + gap < max(initial_start, checkpoint − lookback)`. Простого статуса closed недостаточно. Живые строки сохраняются; архив не является автоматической очисткой, полным журналом ревизий или резервной копией Elasticsearch. Подробнее: [архивы](episode-archives.md).

## Дальнейшие данные для проверки точности

- Собрать обезличенную репрезентативную benign-телеметрию и размеченные сценарии для выбранных детектов. Определить единицу наблюдения, период, происхождение разметки и долю атак.
- С помощью evaluation измерить TPR, FPR и precision на этой выборке; синтетические fixtures не использовать как оценку production accuracy.
- Для текущего источникового контракта проверить аудит и сбор на живом Windows-хосте: сохранение ID, полноту, пропуски и возобновление доставки. XML-экспорты и локальный spool этот этап не заменяют.
- Добавлять Linux-профиль Elasticsearch и сквозной journal replay при переходе к соответствующему детекту. Отдельно документировать версии источников и видимость HTTP/SMB для каждого cross-layer сценария.
- Настраивать исключения только по подтверждённым свойствам источника и доступному enrichment, сохраняя проверки против чрезмерного подавления.

Ограничения существующего bounded replay и live collection остаются действующими; новые гарантии полноты, длительной эксплуатации или обработки данных старше lookback здесь не заявлены.

## Проверка evidence и подготовка к публикации

1. Повторять `make check`, `make check-network` и `make check-elastic` после изменения соответствующих правил или инструментов.
2. После отдельного решения о публикации проверить GitHub Actions на целевом commit; локальное прохождение не подменяет удалённый запуск. Публикация исходников и выпуск версионного релиза учитываются отдельно.
3. Сохранить сопоставимые артефакты проверки чистого commit и провести review заявленной области действия карточек.
4. Обновлять закреплённый ATT&CK/STIX отдельным review: сравнивать изменения каталога, техники/тактики, revoked/deprecated и контекстную разметку. Не заменять версию молча.
5. Продвигать карточку из test только при выполнении всех критериев [методологии](methodology.md), а не по одному успешному тесту.

## Новые платформы и расширение покрытия

Новые адаптеры, включая Splunk и MaxPatrol, добавляются после появления общего набора evidence и проверки конкретного backend. У каждого адаптера должны быть версия, профиль полей, повторяемый запуск и сравнение результатов. Совместимость со Snort требует отдельной проверки; она не следует из успешного Suricata replay.

Новые техники и правила принимаются с теми же требованиями. Масштаб проекта определяется глубиной подтверждённого покрытия, а не количеством непроверенных файлов.
