# Webroot → HTTP: корреляция на Elasticsearch Basic

Сценарий `CORR-WEB-WEBROOT-REQUEST-002` связывает успешное создание/запись файла в
webroot с запросом к тому же ресурсу. Запрос должен содержать точный query key
`cmd`, `exec` или `command`. Результат содержит оба исходных event ID, путь,
область файловой системы, время и найденные ключи — данные для расследования
подозрительной последовательности. Само совпадение не доказывает эксплуатацию,
наличие webshell или выполнение команды.

## Контракт двух источников

Вход — подготовленный JSONL с **плоскими dotted keys**. Нормализатор нативных
file/HTTP-журналов и сборщик на сервере этим пилотом не предоставляются.

| Источник | Обязательные поля |
|---|---|
| Все события | `@timestamp` с timezone, стабильный `event.id`, точный `event.dataset`, `host.id`, `resource.namespace` |
| `host.file` | Канонический абсолютный POSIX `file.path`, строка `file.operation`, JSON boolean `event.success` |
| `web.access` | Канонический абсолютный POSIX `web.resource_path`, строка `url.query` без начального `?` и fragment |

`resource.namespace` — доверенный идентификатор файловой системы или workload,
заданный сборщиком. Один сервер может содержать несколько контейнеров/chroot с
одинаковым `/var/www/html/index.php`; их события не должны соединяться.
Ключ связи — **host.id × resource.namespace × точный путь**. Заголовок HTTP Host
не является доверенной заменой namespace. Если несколько виртуальных хостов или
aliases обслуживают один физический ресурс, upstream mapping может присвоить им
одну область; разные файловые системы должны оставаться разными.

Путь HTTP-ресурса должен быть заранее разрешён с учётом document root, rewrites,
symlinks, контейнеров и mount boundaries. Runtime не выводит файловый путь из URL,
не выполняет percent-decoding пути и не исправляет `..`, повторные `/` или
относительные пути. POSIX-регистр пути сохраняется. Windows paths требуют
отдельного профиля.

Для кандидата `file.operation` должно быть `create` либо `write`, а
`event.success` — `true`. Хорошо сформированные read/open или failed-write
события допустимы на входе, но не дают файлового кандидата. Успешный Linux audit
open с правом записи означает write intent; его нельзя автоматически объявлять
фактической записью. Происхождение и смысл `host.file` должен гарантировать
источниковый контракт развёртывания.

Профиль [`web-correlation-v1`](../profiles/elastic/web-correlation-v1.mapping.json)
проверяет оба dataset, типы, flat-формат, обязательные значения, UTF-8 и диапазон
времени. Отсутствующая область, malformed path/query, integer вместо boolean и
конфликтующий payload с тем же event ID завершают batch ошибкой. Это ошибки входа,
а не отрицательные результаты детекта. ID, host и namespace должны быть
непустыми строками без окружающих пробелов и управляющих символов.

`event.id` должен быть глобально уникален между обоими dataset общего индекса:
одинаковый локальный номер file- и HTTP-журнала без разделения источников не
подходит. Индексируемые keyword-строки ограничены 32766 байт UTF-8, ID — 512 байт.
Query хранится в `_source` без индексации. Некорректные dotted names и конфликты
с mapping/служебными полями отклоняются до отправки batch. Bulk-запись при этом
не становится транзакцией: транспортный сбой может потребовать повторной
доставки тех же неизменных событий.

## Точное условие

- Файл расположен под явно переданным `--webroot`; сходный префикс вроде
  `/var/www/html-other` не подходит. При проверке суффикса регистр понижается:
  поддержаны `.php`, `.jsp`, `.aspx`. Расширение лишь указывает на файл, похожий
  на серверный скрипт; оно не подтверждает настройку обработчика. `.phtml` этим
  пилотом не покрывается.
- Query разбирается один раз, разделитель — `&`, UTF-8 строгий. Ключи
  `cmd`, `exec`, `command` сравниваются точно и с учётом регистра.
  `%63md=x` подходит; `notcmd=x`, `CMD=x`, `mode=cmd%3Dx` и `%2563md=x` — нет.
  Проверяется **наличие ключа**: `cmd` и `cmd=` тоже подходят. Значение не
  интерпретируется как команда. Это отличается от сетевой Suricata-сигнатуры
  с непустым `cmd` и не заявляет эквивалентность двух детектов.
- При окне W=300 секунд запрос должен попасть в
  `[file_timestamp, file_timestamp + W)`. Равное время допускается; ровно через
  300 секунд — уже нет. `--window-seconds` принимает 1…86400.
- Каждый подходящий HTTP event связывается только с последним подходящим file
  event. При равных file timestamps выбирается лексикографически больший event ID.
  Порядок входных строк не влияет на результат; одинаковые повторные события
  учитываются один раз. Несколько HTTP event могут дать несколько кандидатов.

`--start A --end B` задают HTTP timestamps в `[A,B)`. Для связи нужен файловый
контекст `(A−W,B)`, включая записи раньше A. Время нормализуется в UTC с точностью
до микросекунд. Elastic хранит его в `date_nanos`; допустимый диапазон профиля —
от `1970-01-01T00:00:00Z` до `2262-04-11T23:47:16.854775Z` включительно.

## Воспроизведение

Из корня репозитория после `make setup`:

```bash
.venv/bin/python tools/correlate_webshell.py \
  tests/fixtures/correlation/webroot_request.jsonl --webroot /var/www/html
```

Синтетический пример даёт одну пару `file-create` → `request-suspicious`:
`web-01`, namespace `site-1`, `/var/www/html/uploads/example.php`, разница 60 секунд.
Обычный похожий query и запрос другого host не входят в результат; повтор file
события дедуплицируется. `site-1` — условное имя fixture, не универсальное значение
для рабочей среды.

Для конечного replay на бесплатном Basic:

```bash
make lab-up
.venv/bin/python tools/elastic_web_correlation.py --index attck-web-correlation-demo create-index
.venv/bin/python tools/elastic_web_correlation.py --index attck-web-correlation-demo ingest \
  tests/fixtures/correlation/webroot_request.jsonl
.venv/bin/python tools/elastic_web_correlation.py --index attck-web-correlation-demo evaluate \
  --webroot /var/www/html --page-size 2 \
  --start 2026-01-01T00:02:00Z --end 2026-01-01T00:04:00Z
```

Ожидается та же пара. `create-index` не перезаписывает существующий индекс;
повторяйте ingest/evaluate или выбирайте новое имя. Повтор неизменных событий
безопасен; подмена содержимого при прежнем ID отклоняется. Настройки URL и
credentials описаны в [Elastic guide](elastic.md). Лабораторный Compose использует
Basic без trial и платных функций.

Оба источника хранятся в одном отдельном индексе `web-correlation-v1`. Адаптер
читает их через один PIT с `search_after`, затем выполняет корреляцию в Python.
Он проверяет mapping, UUID индекса, типы прочитанных событий, `_id`/event.id,
точность времени, полноту shard-ответов и продвижение pagination. Это конечный
replay; расписание, долговременное состояние алертов и непрерывный web pipeline
не предоставляются.

`--max-events` по умолчанию равен 100000, `--max-alerts` — 10000. Превышение
лимита, timeout, неполный поиск или смена UUID завершаются ошибкой без частичного
успешного результата. `--page-size` управляет размером страницы, а не общим числом
событий. Офлайн-лимит считает все входные строки-события до фильтрации/дедупликации;
Elastic-лимит — прочитанные события обоих dataset в диапазоне поиска, включая
контекст и обычные запросы. Счётчики разных областей входа не обязаны совпадать;
сравниваются ожидаемые пары и evidence. Офлайн CLI отклоняет пустой replay.

## Совместимость и ограничения

Для прежнего host/path пилота namespace теперь обязателен. Старые данные нужно
дополнить проверенной областью из источника; общий вымышленный namespace скроет
разделение контейнеров. Rule ID изменён с `…-001` на `…-002`. Alert ID — полный
SHA256 канонического JSON-кортежа rule/host/namespace/file-event/request-event;
он отличается от прежнего короткого hash с разделителем. Автоматической миграции
старых результатов нет.

Обычный deploy с посещением страницы или загрузка статического файла не должны
создавать кандидата. Но deploy административного скрипта с легитимным `cmd`
запросом может удовлетворить всему условию: такой пример сохраняется как
**benign candidate**, а не объявляется успешно исключённым ложным срабатыванием.
Ручные ожидания и происхождение описаны в [fixtures](../tests/fixtures/correlation/README.md).

HTTP 404/500 не исключаются и не подтверждают выполнение файла. Последняя запись
не доказывает, что файл сохранился после удаления/rename или что ответ получен
именно от него. Вне покрытия: старый webshell без недавнего write, другие
расширения/ключи, команда только в POST body, данные за границей окна, неполные
журналы и ошибочный mapping namespace/path. Обогащение процессами web-сервера,
содержимым файла и контекстом deploy нужно проверять отдельно.

Два T1190 Hunt-файла остаются design-only. Исправление их описания не добавляет
операторы в Hunt DSL: исполняемый путь здесь — отдельный correlation runtime и
Basic-адаптер. Прохождение synthetic fixtures не измеряет эксплуатационные
precision/TPR/FPR; текущие результаты запусков перечислены в [отчёте](validation_report.md).
